## 1. Setup and build

### 1.1 Toolchain

- **Node 24** (built with 24.13.0). `node -v` must print `v24.x`. Do not change the system Node; if you need a different version for a check, use a throwaway directory and `PATH`-prefix it.
- **Python 3.10+** with `pip` — needed only to re-execute the Python/Django track (3.12+ if you want to run Django 6.1 itself; 3.10 runs Django 5.2 LTS with identical code).
- **Playwright Chromium** for screenshots: `cd website && npx playwright install chromium`. If `PLAYWRIGHT_BROWSERS_PATH` is set in your shell, Playwright looks there; otherwise `~/.cache/ms-playwright`.
- Not installed on the first-wave machine, and therefore **not executed in the first wave**: Ruby, Go, Java (JDK 25), .NET 10, PHP 8.5, Rust (cargo), Dart. If you have any of them, §4.4 tells you what to run. Angular CLI 22 also needs **Node ≥ 24.15** — see the Angular card in §4.4.

### 1.2 Build and serve

```bash
cd website
npm ci
npm run build          # node build/index.js → public/ (281 pages, ~4 s)
npm start              # Express 5 on http://localhost:31803
```

`public/` is generated. **Never hand-edit anything under `public/`**; your edit is destroyed by the next build. The production process is `pm2` process `dtc-guide` on port 31803 (`pm2 restart dtc-guide` after a build you want live).

Build flags (environment variables):

| Variable | Effect |
|---|---|
| `DTC_DEV=1` | Build continues past verification-ledger gaps (warns instead of failing); the verification gate warns instead of failing. Use while a content pass is in progress. **Sign-off runs must not set it.** |
| `DTC_SKIP=a,b` | Skip named gates in `npm test` (names in §2). e.g. `DTC_SKIP=prep` while iterating on a single page. |
| `NODE_ENV=production` | `server.js` writes a one-line request log to stdout (method, path, status, ms, UA). The pm2 process runs with it set. |
| `DTC_VERBOSE=1` | Gates list every failure instead of the first 60. |
| `BASE_URL=http://…` | `npm run screenshots` shoots a running server instead of starting its own. |

|---|---|

| # | Gate | What it asserts | Fails when |
|---|---|---|---|
| 0 | `build` | `node build/index.js` completes | A renderer throws; a page has no `content/verification.json` entry (unless `DTC_DEV=1`); a runnable file does not print `ok:` |

### 2.1 The ledger

```bash
npm run verify:ledger        # node scripts/verify-ledger.js
```

Regenerates `content/verification.json` and `qa/VERIFICATION.md` from the registry, the build manifest (`build/.manifest.json`, written by the build) and the override frontmatter. **Run it after every content change, then rebuild**, otherwise gate 7 fails.

How it decides `exec` per page: T-EXERCISE → `ran` (gate 5 proves it); pages with a runnable prep file → `ran` (gate 3 proves it); pages with an override → whatever the override's frontmatter `exec:` says (the author's claim, with `verified_note` as the evidence); pages whose only code is standalone JS → the ledger script actually executes each block under node with a 10 s timeout and an `assert` prelude (`ran` if all pass, `not run` if any fails or if the page also has non-JS code it cannot run); no code at all → `n/a`. Flags: `--no-exec` (skip block execution), `--who="…"`.

**Never edit `verification.json` or `qa/VERIFICATION.md` by hand.** Change the override frontmatter and regenerate.

**The ledger executes what you write.** Every standalone JavaScript block in a page — including blocks in `content/overrides/` — is run under `node` by `verify:ledger`, and every runnable prep file by gate 3. Both run under Node's permission model (`--permission`): a block can read its own temp file (prep files: their own directory), and cannot write, spawn processes, start workers, load addons or see the builder's environment. A block that needs any of that is reported as `not run`, which is the correct answer for it — do not loosen the flags in `scripts/verify-ledger.js` / `build/test/prep.js` to make a page green.

## 4. Content verification protocol

The loop for every page in your block:

1. Open the page and its registry entry side by side.
2. Check each **Fact** the registry lists (H2s, counts, framework) — gate 1 already asserts the machine-checkable ones; you check the human ones (lede says what the page does, chips truthful, images relevant, links point where the text says).
3. Open the primary docs named in the page's Source card and in the card below for the page type. Read the page **against** them: every API, flag, command, version and complexity claim.
4. Run what can be run (§4.4). Compare actual output with what the page states.
5. Log every defect in `qa/findings.md` (§5.2). Fix it (§1.4). Rebuild, `npm run verify:ledger`, `npm test`.
6. Tick the page's acceptance boxes in `SITEMAP-AND-USER-STORIES.md` with a one-line evidence note (`✓ 2026-11-xx — ran under node 24.13, output matches`).

Defect classes — use these words in the `severity`/`class` columns so findings can be grouped:

| Class | Examples | Default severity |
|---|---|---|
| `outdated-api` | removed export, renamed option, deprecated hook still taught as current | high |
| `wrong-command` | a shown command does not run as written on the current stable release | high |
| `wrong-complexity` | Big-O stated differently from the complexity cheat-sheet or from the code | high |
| `output-mismatch` | the example says it prints X; it prints Y | high |
| `dead-link` / `dead-image` | 404, redirect to an unrelated page, placeholder image | medium |
| `attribution` | missing licence/credit, or any forbidden mention (also a build failure) | high |
| `cohort-logistics` | Slack/Zoom/class-schedule sentences left in | low |
| `brand` | palette, type, spacing, component deviates from DESIGN-REFERENCE | medium |
| `a11y` | focus, contrast, alt text, keyboard trap | medium / high if blocking |
| `typo` | spelling, grammar in *our* text (not in quoted source) | low |

### 4.1 Override frontmatter (what a refreshed page must carry)

```yaml
---
title: "…"                      # page title as the registry states it
framework: Django               # T-LANG only; must equal the registry's Framework fact
version: "6.1"                  # T-LANG only; the yellow chip
lede: "…"                       # ≤ 40 words
updated_from: "…"               # what the 2021 original was
verified: 2026-11-02            # date you checked it
docs:                           # absolute URLs of the primary docs you read it against
  - https://docs.djangoproject.com/en/6.1/
exec: ran                       # ran | not run | n/a  — only `ran` if you actually executed it
verified_note: "…"              # how it was run (versions, machine, what passed), or why it was not
changes:                        # every substantive change from the original, one line each
  - "…"
---
```

`exec: ran` is a claim you are making in writing. If you did not run the code on the version the page names, say exactly what you did run (e.g. "run on Django 5.2 LTS / Python 3.10; identical code") in `verified_note` — the first wave did this for Python and Angular and the notes are visible on the pages.

## 4.6 The Todos contract (backend and frontend guides)

Every backend api page and every frontend page implements one contract, so any frontend works with any backend:

| Request | Response |
|---|---|
| `GET /health` | 200 `{"ok":true}` |
| `GET /todos` | 200 `[{id,subject,details}]` ordered by id |
| `GET /todos/:id` | 200 the object, or 404 `{"error":"not found"}` |
| `POST /todos` `{subject,details}` | 201 the new object |
| `PUT /todos/:id` `{subject,details}` | 200 the updated object, or 404 |
| `DELETE /todos/:id` | 204 with no body, or 404 |
| blank or missing `subject`/`details`, or malformed JSON | 400 `{"error":"…"}` |

Objects contain exactly `id` (integer), `subject`, `details`. No trailing slashes. CORS: any origin, methods GET POST PUT DELETE OPTIONS, header Content-Type. The process reads `PORT`. `website/scripts/check-todos-api.mjs` (copied verbatim into each repo as `check.mjs`) asserts all of it; a page may only say `exec: ran` for its api step when that script printed 16/16 PASS against the deploy named in `verified_note`. Live deployments and repos as of 2026-11-07: see the "Pick any backend" table on any frontend page.
